# make-kids-picturebooks Skill 第一性原理全面审计

审计日期：2026-10-24  
审计范围：`D:\宝宝绘本制作\.codex-github-sync\phase1-flow-reduction`  
审计方式：只读静态审计、依赖关系审计、运行包审计、资产体积审计、聚焦回归测试  
本轮状态：未修改生产代码、未删除功能

## 一、先回答最根本的问题：这个 Skill 的最小交付是什么

不从“现在有多少文件”出发，而从用户最终需要什么出发。

默认目标是：

> 把一个经过来源和知识门禁的主题，转化为一个可续做、可审核、可追溯的儿童知识绘本项目，并交付无字逐页图片、独立正文和确定性的交付记录。

因此，默认生产链的最小闭环只有六类能力：

1. **输入与知识边界**：确认来源、年龄、知识白名单和科学追溯。
2. **故事与页面任务**：把知识变成故事、分镜、页面任务和视觉证据。
3. **资产绑定**：锁定角色、画风、参考图、版本和页面依赖。
4. **生产门禁与队列**：正式生图前做 strict 预检，逐页串行推进，支持失败记录和续做。
5. **审核状态**：区分机器生成成功、人工视觉审核通过和最终可发布。
6. **纯图交付**：保留源图、独立正文、哈希、缩略图和发布边界。

凡是不直接服务这六类能力的内容，都不应进入默认核心包；但可以作为按需插件、历史兼容包或开发包保留。

## 二、总判断：功能模块化了，但发布模块化还不够

### 2.1 已经具备的模块化

当前 Skill 已经有清晰的职责分层：

| 模块 | 主要职责 | 判断 |
|---|---|---|
| 输入选择 | 来源安全、年龄、主题筛选、改编边界 | 核心，必须保留 |
| Research 门禁 | 四文件研究包、白名单、逐句 claim trace、页面科学证据 | 核心，必须保留 |
| 故事与分镜 | 教育目标、视觉事件、页面任务、连续性 | 核心，必须保留 |
| 资产系统 | 角色、画风、参考图、版本、哈希和发布 | 核心，但应隐藏内部层次 |
| 页面与连续性 | page manifest、页面依赖、跨页状态 | 核心，必须保留 |
| 生产队列 | claim、submit、complete、失败、恢复、授权、计时 | 核心，必须保留 |
| 纯图交付 | 归一化、复制、哈希、contact sheet、delivery manifest | 核心，必须保留 |
| 审核与发布 | review、pre-delivery、release receipt | 核心，必须保留 |
| 社媒成品 | 文字合成、3:4 图文输出和社媒验收 | 按需分支 |
| PDF/打印 | 阅读版、拼版、字体、PDF 验收 | 历史/按需分支 |
| 迁移、归档、诊断 | 旧项目兼容和工程排查 | 历史/开发分支 |
| 测试、评测、计划 | 防回归和开发过程 | 开发包，不应进入运行包 |

`SKILL.md` 已经把默认路径收敛为：

```text
输入契约 → 知识门禁 → 故事/整本分镜 → 资产锁定
→ 一次整本 strict 预检 → 串行逐页生图
→ 页面审核 → 局部返工 → pure-images 确定性交付
```

这说明“流程设计”已经完成第一阶段的模块化。

### 2.2 尚未完成的模块化

代码和资产仍然主要放在同一个默认运行包中：

- 默认运行包当前扫描到 **277 个文件**；
- 原始体积约 **145.35 MB**；
- 实际 ZIP 约 **139.77 MB**；
- 其中 `projects/` 测试产物有 **166 个文件、115.36 MB**；
- `projects/` 占当前运行包原始体积约 **79.4%**。

所以当前状态可以准确描述为：

> **业务职责已经模块化，发布边界还没有模块化。**

## 三、最重要的审计发现

### P0：默认打包器会把本地 `projects/` 一起打包

证据：

- `scripts/package_skill.py` 的 `RUNTIME_EXCLUDED_DIRS` 当前包含 `.github`、`.pytest_cache`、`docs`、`evals`、`tests`，但没有 `projects`。
- 当前本地运行包包含 166 个 `projects/` 条目。
- 实际构建测试包时，压缩包确实出现了 `make-kids-picturebooks/projects/...`。
- 当前 `projects/` 未被 Git 跟踪，但工作区存在未跟踪目录；因此“干净 GitHub 检出”暂时不一定复现，“本地打包”已经可以复现。

这不是单纯的体积问题：项目中包含故事、提示词、研究记录、生成图片、交付记录和测试报告，可能包含用户私有资料。Skill 自己的发布说明又明确写着“任何用户书籍、儿童资料、角色参考或生成项目都不进入公开包”，两者目前不完全一致。

**结论：** `projects/` 不应进入运行包，也不应默认进入 GitHub。

**优先级：P0。**

**建议：**

1. 将 `projects` 加入运行包排除目录。
2. 将 `projects/` 加入仓库 `.gitignore`，防止测试产物误提交。
3. 增加一个打包测试，明确断言压缩包不得出现 `projects/`。
4. 不删除本地测试项目；只改变发布边界。

仅做第 1 步，当前本地运行包就可从约 145.35 MB 原始体积降到约 29.99 MB。

### P1：默认包混入大量按需资产和按需依赖

当前资产体积：

| 内容 | 体积 | 默认 pure-images 是否必须 |
|---|---:|---|
| `assets/characters/core-v1.2` | 2.25 MiB | 是，默认核心角色资产 |
| `assets/characters/core-v1.3` | 14.08 MiB | 否，STYLE-06/阶段性显式资产 |
| `assets/style-06-v0.1` | 2.64 MiB | 否，按需画风分支 |
| `assets/kidsbook-print.ttf` 及证明文件 | 8.97 MiB | 否，PDF/打印/文字合成分支 |

当前 `requirements.txt` 同时安装：

```text
Pillow
reportlab
pypdf
fonttools
PyMuPDF
```

默认 pure-images 主链实际需要的图像处理能力主要是 Pillow；其余依赖集中在 PDF、打印、字体和历史成品分支。

**结论：** 默认包把“可以做”误当成“默认必须装”。

**建议：** 分成：

- `core`：默认纯图生产和审核所需脚本、核心参考资产、Pillow；
- `print-pdf`：PDF、打印、拼版、字体和对应依赖；
- `social-output`：图文合成、社媒验收和对应字体/版式资源；
- `legacy-diagnostics`：迁移、归档、完整诊断和兼容工具；
- `dev`：测试、评测、报告和开发计划。

这不是删除能力，而是把能力从默认路径移到真正需要它的边界。

如果把可选资产也移出核心包，核心运行包的原始内容可接近 **3 MiB** 量级；实际压缩包大小仍需在实现后重新测量，不能直接把这个原始估算当作最终 ZIP 大小。

### P1：仓库中的 `MANIFEST.json` 已经不是当前运行输入的准确快照

对比结果：

- 当前静态 `MANIFEST.json` 记录 **109 个文件**；
- 当前运行打包逻辑在排除 `projects/` 后发现 **111 个非项目文件**；
- 静态清单缺少新增的：
  - `scripts/clone_project_for_test.py`
  - `scripts/generated_image_path.py`
- 当前有 **9 个文件的规范化哈希不一致**，包括 `SKILL.md`、`production-workflow.md`、`generation_queue.py`、`workflow.py` 等。

`scripts/package_skill.py` 会在真正打包时重新生成包内 `MANIFEST.json`，因此当前测试仍能通过；但仓库根目录的静态清单会误导人工审查，也没有被 CI 验证为与当前源文件一致。

**第一性原理判断：** 同一份发布事实不应该有两个没有同步保证的权威来源。

**建议二选一：**

1. 删除仓库根目录静态 `MANIFEST.json`，只把生成的清单放在发布包内；或
2. 保留它，但让 CI 生成包内清单后与根目录清单做精确比较。

更简洁的方案是第 1 种。删除前先更新测试和发布流程，不能直接删文件造成新的断链。

### P1：核心代码和兼容代码仍在同一运行入口目录

`scripts/` 当前有 43 个 Python 文件。静态导入分析显示：

- 从统一入口 `workflow.py` 可递归到约 **20 个核心模块**；
- 另有约 **23 个脚本没有被默认入口导入**，其中大部分属于按需、历史、诊断、打包或测试辅助。

未被默认入口导入不等于废代码，因为其中一些是用户明确请求时的 CLI 入口。但它说明现在可以进一步形成清晰的发布模块边界。

可明确归入按需/历史层的脚本包括：

- PDF/打印：`accept_book.py`、`export_book.py`、`render_book.py`、`validate_exports.py`、`impose_booklet.py`、`prepare_font.py`；
- 社媒成品：`render_social.py`、`render_social_book.py`、`accept_social_book.py`、`preflight_image_generation.py`；
- 历史/诊断：`migrate_social_only_layout.py`、`incremental_archive.py`、`diagnose_project_paths.py`、`project_state.py`；
- 工程发布辅助：`package_project.py`、`production_metrics.py`、`prepare_character_references.py`；
- 测试辅助：`clone_project_for_test.py`、`generated_image_path.py`。

**结论：** 这些脚本暂时不应删除，但不应和默认核心包平铺在同一发布层。

### P1：三个大模块存在结构压缩空间，但不适合直接删除

当前最大的生产脚本：

| 文件 | 行数 | 第一性原理拆分方向 |
|---|---:|---|
| `generation_queue.py` | 2348 | 文件锁/路径、计划构建、请求生命周期、授权、队列状态、CLI 分层 |
| `project_preflight.py` | 988 | 输入快照、资产、研究/内容、路径、审核、图片、输出目标分成检查器 |
| `build_pure_image_delivery.py` | 749 | 输入解析、图片校验、规范化、清单生成、原子发布分层 |
| `production_metrics.py` | 660 | 事件归并、生命周期统计、时间统计、输出格式分层 |

这些文件“大”不等于功能冗余。它们承载的是生产安全边界，直接删代码会降低可靠性。

正确的压缩方式是：

- 保持外部 CLI 和函数接口不变；
- 先用测试固定现有行为；
- 再把内部按职责拆成私有模块；
- 最后让旧入口只做兼容转发。

不建议现在为了减少文件数而把它们重新合成一个更大的脚本，也不建议直接删除内部校验。

## 四、哪些看起来重复，但实际上不能删

### 4.1 `production_timing.py` 和 `production_metrics.py`

两者不是重复：

- `production_timing.py` 负责记录阶段事件和可观测时长；
- `production_metrics.py` 负责读取队列/事件并汇总指标。

这是“采集”和“分析”的自然分离。可以统一字段和命名，但不应删除其中一个。

### 4.2 `asset_catalog.py`、`asset_resolver.py`、`style_lock.py`、`release_character_bundle.py`

这四层分别对应：

- 目录和声明；
- 运行时解析和页面绑定；
- 文件哈希与篡改检测；
- 资产包发布验证。

它们的用户入口可以减少，但职责不能合并成一个不透明的“大资产脚本”，否则会失去边界和可追溯性。

### 4.3 `review_checklist.py`

它是只读汇总器，调用已有 `project_preflight`，没有复制一套新的规则。因此它不是规则重复，而是人工审核工作台。可以继续保持为按需工具，不应删除。

### 4.4 测试和评测文件

测试目录文件很多，但主要由测试模块、夹具和素材组成。当前最近一次完整回归为：

```text
537 passed, 2 skipped, 448 subtests passed
```

本轮审计聚焦测试为：

```text
26 passed
```

测试可以分层、移到 dev 包，但不应为了“看起来更少”而删除。删除测试只会把复杂度转移到未来排错。

## 五、资产层的额外压缩机会

发现以下两个版本中存在完全相同的 PNG：

```text
assets/characters/core-v1.2/reference/core-character-assets-v1.2.png
assets/characters/core-v1.3/reference/core-character-assets-v1.2.png
```

两者 SHA-256 相同，单个文件约 2.30 MB。

但 `core-v1.3` 的 manifest 和 receipt 把这张图写成了自己的包内文件，直接删除会破坏自包含性和现有哈希证明。因此：

- **可压缩空间：约 2.30 MB；**
- **当前不可直接删除；**
- 必须先设计跨版本引用或新的资产包去重协议，再更新 manifest、receipt、测试和发布清单。

这是第二阶段优化，不应作为本轮第一优先级。

## 六、文档是否还能压缩

当前文档体量并不构成主要性能问题：

- `SKILL.md`：77 行；
- `references/production-workflow.md`：213 行；
- `README.md`：74 行；
- `RELEASE.md`：69 行。

`SKILL.md` 和 `production-workflow.md` 有少量默认链、入口和分支说明重复，但总体已经遵守“入口路由 + 详细参考”的方向。

文档压缩建议排在打包边界之后：

1. `SKILL.md` 只保留触发条件、默认主链、硬约束和 reference 路由；
2. `production-workflow.md` 只保留默认生产详细流程；
3. 社媒、打印、历史迁移的细节留在独立 reference；
4. `README.md` 只做安装和最短使用说明；
5. `RELEASE.md` 只做版本变化和兼容边界。

预计只能减少少量文本，不会像拆分运行包那样显著提高运行效率，因此不是第一优先级。

## 七、最终分类：现在能不能删

### 可以立即从默认发布包移出的内容

- `projects/`：测试项目和生成产物；

“移出默认包”比“删除仓库文件”更安全，能保留兼容能力。

### 可以考虑删除，但必须先更新发布流程的内容

- 根目录静态 `MANIFEST.json`：如果决定只保留包内生成清单；
- 旧的发布元数据副本：只有确认不再承担 GitHub 审查或版本追溯职责后才删除。

### 暂时不能删除的核心内容

- `SKILL.md`、`production-workflow.md`、`input-selection.md`、`research-input-gate.md`；
- `content_gate.py`、`project_preflight.py`、`generation_queue.py`；

- `build_pure_image_delivery.py`、`release_pure_image_delivery.py`；
- 页面清单、连续性、授权、失败状态、哈希和审核证据；
- 现有核心测试。

### 不建议继续增加的内容

- 新的总入口；现在 `workflow.py` 已经足够；
- 第二套科学内容门禁；当前 `content_gate.py` 已是规则源；
- 第二套页面事实源；`page-manifest.json` 已承担该职责；
- 默认多套图片候选、默认并行调用或默认 PDF/社媒输出；
- 只为兼容旧流程而复制一份新状态机。

## 八、建议的最小重构路线

### 第 1 阶段：先修发布边界，不改生产行为

1. 排除 `projects/`；
2. 将 `projects/` 加入 `.gitignore`；
3. 增加“运行包不得含项目产物”的测试；
4. 重新生成或移除根目录静态 `MANIFEST.json`；
5. CI 验证最终包内 manifest，而不是只检查版本字符串。

这是收益最高、风险最低的一组改动。

### 第 2 阶段：拆分核心包和可选包

1. 核心包保留默认 pure-images 主链；
2. 打印/PDF 作为 `print-pdf`；
3. 社媒图文作为 `social-output`；
4. 历史迁移、归档和完整诊断作为 `legacy-diagnostics`；
5. 测试和评测作为 `dev`；
6. 保留旧 CLI 路径的兼容转发，避免历史项目立刻失效。

### 第 3 阶段：减少启动耦合

`workflow.py` 当前在模块加载阶段就导入交付发布模块。可以改成按子命令延迟导入：

- `doctor` 只加载预检；
- `resume` 只加载预检和队列；
- `deliver` 才加载发布模块。

这会减少默认入口的加载面，但不改变任何业务规则。

### 第 4 阶段：按测试保护的大模块内部拆分

按以下顺序进行：

1. `generation_queue.py`；
2. `project_preflight.py`；
3. `build_pure_image_delivery.py`；
4. `production_metrics.py`。

每次只拆一个边界，先写或补充失败测试，再实现，再跑完整回归；不做同时改名、改 schema、改 CLI 的大爆炸重构。

## 九、效率影响判断

### 会提高效率的部分

- 删除 `projects/` 进入运行包：显著降低本地打包、上传和安装时间；
- 按需依赖：减少默认环境安装时间和依赖冲突；
- 按需资产：降低包下载和解压成本；
- 按命令延迟导入：减少默认入口启动负担；
- 保留唯一规则源：减少重复判断和维护成本。

### 不会降低默认生产能力的部分

- 把 PDF、打印、社媒移到可选包，不影响默认 pure-images；
- 把测试和项目产物移出运行包，不影响生产队列；
- 将大模块内部拆分，只要保持外部接口和 schema 不变，不影响业务结果。

### 需要防止的低效改法

- 为“模块化”新建更多总入口；
- 把相同规则复制到新模块；
- 为了减少文件数把所有逻辑合并进一个超大文件；
- 未更新 receipt 就删除重复资产；
- 在没有测试的情况下重命名 CLI 或改变项目结构；

## 十、最终结论

当前 Skill **已经具备可用的业务模块化和高可靠默认生产闭环**，不是需要推倒重来的系统。

> **先把发布边界做干净，再把可选能力分包，最后对大模块做受测试保护的内部拆分。**

按收益/风险排序：

1. **立即处理：** `projects/` 不得进运行包，且加入 `.gitignore`；

5. **暂缓处理：** v1.2/v1.3 重复 PNG 去重，等资产引用协议成熟后再做。

## 十二、第三阶段：生成到交付链路闭合

在后续故事测试中发现，核心生产逻辑虽然能够生成图片，但“队列完成 → 页面清单 → 纯图片交付”之间仍存在工程断点：队列知道图片已经完成，页面清单却可能仍是空路径；测试副本排除图片后还可能残留失效路径；调用方还需要手动分别记录提交和完成。

本轮按第一性原理只补三条必要连接，不引入新的业务规则：

1. `complete_job` 完成图片校验后，原子同步对应页面清单的 `current_image_path`，统一使用书籍级 `books/<book>/<version>/images/page-XX.png` 作为正式路径。
2. 新增 `generation_queue.py finish-page` 和 `workflow.py finish-page` 高层入口，一次记录已观察到的后端提交并完成页面；底层“没有观察到提交不得完成”的生命周期约束保持不变。
3. 测试克隆排除图片后，自动将页面清单中不存在或不安全的图片引用重置为 `null`，避免旧路径污染新测试。

### 实测结果

- 新增端到端回归：页面完成后直接调用交付构建，不再复制图片到 `content/images`。
- 修正运行时脚本后的 `MANIFEST.json` 已重新生成并通过清单一致性测试。
- 全量测试：`548 passed, 2 skipped, 448 subtests passed`。
- 依赖检查：`python -m pip check` 输出 `No broken requirements found.`
- 差异检查：`git diff --check` 通过。

因此，默认图片生产链路现在形成：

> **授权 → claim → 生图 → finish-page → 页面清单同步 → 交付构建**

本轮没有自动通过视觉审核、知识审核、版式审核、文字-图像匹配或连续性审核。这些仍是有意保留的人类/独立门禁，避免把“工程完成”误报为“内容验收完成”。
