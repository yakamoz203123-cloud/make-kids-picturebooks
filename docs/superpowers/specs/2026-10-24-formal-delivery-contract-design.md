# Formal Delivery Contract Alignment Design

## Intent

把“生产可用”和“正式可交付”之间的契约对齐，并完成已修复豆子项目的正式交付收尾。修复必须保留历史输入、保留真实人工审核边界，并让未来项目在缓存/生成阶段更早发现正式画布不合规问题。

## Goals

- 正式 3:4 项目在生成队列和正式预检中统一要求 `1080×1440`、RGB、无 alpha。
- 生成队列不能把 `1086×1448` 这类仅比例正确的图片标记为正式缓存。
- 修复 Windows 默认控制台下 `content_gate.py` 中文 JSON 输出失败的问题。
- 为修复副本生成可追溯的正式 1080×1440 图片，保留原 1086×1448 输入。
- 对最终图片完成真实逐页视觉审核，并保存现有验收契约要求的 `review.json` 和页面证据。
- 保持原始 `delivery-input` 不变，所有项目修复只作用于 `delivery-input-repaired`。

## Non-goals

- 不放宽正式交付尺寸要求。
- 不把 `pending` 批量改为 `passed`，不生成虚假的人工审核证据。
- 不删除或覆盖历史 1086×1448 原图。
- 不重新设计整套验收 schema，不新增重复的审核文件。
- 不强制旧版非正式/历史项目使用新的正式画布契约。

## Root cause and boundary

当前队列的图片验证只检查图片可解码、最小边长和声明比例；正式预检才检查精确 `1080×1440`。因此 1086×1448 会在队列中成为 `cached`，但在正式交付时被阻断。页面 `pending` 和缺失 `review.json` 则表示项目完成了生产准备和队列初始化，但没有完成最后的人工验收阶段。样式警告来自项目只保存了全局样式 ID/版本，没有保存本地批准证据。

## Approaches considered

1. **只修当前项目**：输出合规图片和审核记录，但保留队列的宽松验证。短期可交付，未来仍会重复相同问题，拒绝。
2. **契约对齐并修当前项目**：增加正式画布的精确验证、修复 CLI 编码，同时完成当前项目的正式图片和人工证据。推荐，解决根因且不改变历史项目兼容性。
3. **放宽正式交付门禁**：接受 1086×1448 或缺失人工证据。会把真实风险隐藏为“通过”，拒绝。

## Chosen design

### 1. Formal canvas contract

从现有页面布局和正式 profile 解析期望画布；正式 `xiaohongshu-feed-3x4` 使用精确 `(1080, 1440)`。生成队列在有正式画布契约时执行精确检查，旧版没有正式画布声明时保持比例兼容。错误必须包含实际尺寸和期望尺寸。

### 2. CLI output contract

所有面向用户的 JSON CLI 输出统一使用 UTF-8，优先通过 `sys.stdout`/`sys.stderr` 的安全重配置解决，不改变文件 JSON 的 UTF-8 存储约定。Windows 默认 GBK 控制台不能再导致一个实际通过的 gate 返回编码异常。

### 3. Historical project repair

- 将现有 `native/page-XX-native.png` 复制到项目 review recovery 区域作为历史输入留档。
- 使用现有确定性纯图片交付逻辑生成正式 `1080×1440`、RGB、无 alpha 的页面源图，并更新正式页面引用和哈希。
- 逐页查看最终图片；只有实际确认后才把页面审核字段写为 `passed`，并保存具体证据。
- 创建项目本地 `review.json`，包含工程、内容、视觉和真实阅读证据；未进行真实共读时保持真实阅读状态为 `pending`，不冒充完成。
- 保存样式批准证据或明确可验证的全局依赖记录，避免只留不可审计的 ID。

### 4. Verification boundary

- 单元测试验证新画布契约、历史兼容、UTF-8 输出和不覆盖原图。
- 生产前严格预检必须通过，生产依赖缺失和越界必须为 0。
- 正式交付预检必须在图片、页面证据和本地样式证据补齐后通过。
- 最终检查原始 `delivery-input` 的哈希/文件列表未变化。

## Success criteria

- 新增/更新的测试全部通过。
- `1086×1448` 在正式项目队列中不再被接受为正式缓存。
- Windows 默认控制台运行 `content_gate.py validate-packet` 不再出现 `UnicodeEncodeError`。
- 修复副本正式图片全部为 `1080×1440 RGB`，原图仍可恢复。
- 修复副本的研究包、故事追溯、生产依赖和正式交付预检均通过；真实阅读证据按实际情况保持 `pending`。
- 原始项目未被修改。
