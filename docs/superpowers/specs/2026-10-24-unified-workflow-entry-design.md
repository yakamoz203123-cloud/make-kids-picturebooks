# 统一生产入口设计

## 背景

当前 Skill 的底层能力已经按职责拆开，但用户仍需要记住多个脚本、参数和先后关系。这个问题不是“缺少功能”，而是“同一条生产链暴露了太多内部接头”：预检、队列初始化、授权、领取和交付都能单独调用，容易造成重复操作、漏步骤或误把技术成功当成发布成功。

## 第一性原理

用户真正需要的只有三种判断：

1. 这个项目现在能不能继续？
2. 现在是否可以安全地推进下一页？
3. 这个交付包能不能进入正式发布？

因此增加一个薄的统一入口，把现有模块编排成三个动作；底层模块继续各自负责规则，不在入口层复制校验逻辑。

## 方案比较

| 方案 | 结论 | 原因 |
|---|---|---|
| 新增薄编排器 `workflow.py` | 采用 | 新入口简单，复用现有门禁、队列、授权和交付实现，改动面小 |
| 把所有能力合并进一个大脚本 | 不采用 | 会把内容门禁、队列状态和交付规则耦合，后续维护更慢 |
| 重写队列和审批状态机 | 不采用 | 没有解决用户操作复杂度，且风险远大于收益 |

## 用户入口

### `doctor`

只读检查一个项目，默认执行现有 `pre_generation/strict` 预检。输出项目是否可生产、页数、阻断项、警告和下一步建议。它不创建队列、不授权、不调用图片模型。

### `resume`

初始化或复用现有生产队列，保持默认单页串行推进，找出下一页：

- 有正在运行的页面时返回 `waiting`，不再领取新页；
- 没有待处理页面时返回 `complete`；
- 没有用户授权时返回 `authorization_required`，不自动批准；
- 明确传入一次授权时，只消费一次有限授权并领取一页，返回 `claimed`；
- 遇到未知请求、耗尽重试次数或失效门禁时，沿用底层安全错误，不自动恢复或绕过。

入口只负责把“授权一次并领取下一页”串起来，实际状态变更仍由 `generation_queue.py` 原子完成。

### `deliver`

直接委托现有 `release_pure_image_delivery.py`。它仍然执行 `pre_delivery/strict`、检查交付验证和人工审核边界，并且只写入唯一的发布回执；统一入口不新增发布规则。

## 明确不改变的内容

- 不改变 `schema_version: 1`、图片模型并发和默认串行策略；
- 不跳过 Research、内容、资产、路径、连续性或人工审核门禁；
- 不自动批准、不自动恢复 `pending_unknown`、不自动重试；
- 不删除低层脚本，诊断和历史兼容仍可直接使用；
- 不让技术生成成功等同于视觉审核通过或正式发布。

## 验证标准

- 三个入口都能从 Python API 和命令行返回机器可读结果；
- `resume` 在无授权时安全停止，在有授权时只领取一页；
- 已有队列和有效预检回执继续复用，统一入口不引入额外的整本扫描；
- `deliver` 只做委托，不复制发布逻辑；
- 旧测试、Skill 指导测试和打包检查继续通过。
